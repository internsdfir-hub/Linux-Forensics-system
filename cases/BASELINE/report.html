Key observations

  • Login record file var/log/btmp is empty

    The file var/log/btmp, which the system uses to record logins, exists but contains no usable records, even though 4 logins are recorded elsewhere in the logs.

    Clearing these files is a standard way of hiding that someone logged in. They are binary, so they are usually emptied rather than edited.

  • Insecure SSH configuration: PermitRootLogin yes

    PermitRootLogin yes - the SSH daemon permits direct root login, so the root account can be attacked over the network with no user attribution

    An over-permissive SSH daemon widens the network attack surface: direct root login, empty passwords, or password authentication all let an attacker in over the network, often with no user attribution.

  • Command history for msfadmin is missing or empty

    The account msfadmin has 7 recorded login sessions, but its command history file is missing.

    Someone who logs in and runs commands normally leaves a history file behind. An account that logged in many times but has nothing recorded usually means the history was deleted, or the shell was started in a way that avoids writing it. Either is a deliberate act.

Recommended next steps

  1. Compare against the same file's rotated copies and against the journal, which records logins separately. If the journal shows logins the binary file does not, the file was cleared.
  2. Harden /etc/ssh/sshd_config: set PermitRootLogin no, PermitEmptyPasswords no, prefer key-based authentication, then restart sshd.
  3. Ask whether msfadmin is a service account that never uses an interactive shell - that would explain it innocently. If it is a person's account, treat the missing history as intentional and look at what else happened during those sessions.

Appendix A — Methodology, limitations and tool audit

How this report was produced

  1. Artifacts were collected read-only on the target. Each file was stat'd, copied, and the copy hashed; the source was stat'd again so that growth during collection is recorded as an observation, not an error.
  2. At ingest every file was re-hashed against the collection manifest. Mismatches were quarantined and excluded from analysis.
  3. Parsers translated each artifact into normalised events. A parser that fails does so alone; the run continues and the failure is recorded.
  4. Correlation rules ran over the normalised events. Every rule is explainable: it names its threshold and the exact events it fired on. No machine learning is used anywhere in this tool.

Coverage

86 artifact(s) were recorded. 65 parsed successfully, 21 had no parser that claimed them, and 0 failed during parsing.

Appendix B — What we could not determine

Absence of evidence is itself evidence, and stating it plainly is part of an honest examination.

  • 21 collected artifact(s) had no parser that claimed them. Their contents were not analysed.
  • This examination sees only what the collector captured. Anything an intruder deleted before collection, or that was never written to disk, is outside its reach.
  • Timestamps carrying a confidence of year_inferred were reconstructed from file modification times, because classic syslog lines record no year.

Appendix C — Glossary

Artifact
A file or command output collected from the target host.
Normalised event
One record parsed from an artifact into the tool's common schema, so that evidence from different sources can be compared on a single timeline.
Finding
A correlation rule firing on specific events. A finding is an indicator for a human to judge, not a conclusion.
Confidence
How strongly the evidence supports a finding: High, Medium or Low.
Chain of custody
The record proving evidence has not changed since collection: a hash taken at collection and re-verified at ingest.
Quarantined
An artifact whose hash did not match the manifest. It was excluded from analysis because anything derived from it would be unattributable.
Tool-generated
An event caused by the collection itself, tagged so the tool does not report its own operator as suspicious activity.
